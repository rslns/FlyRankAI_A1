Predicting CTR Improvement from Search Performance Signals

A decision-support analysis using the FlyRank ML Internship dataset

Abstract

This study asks whether search-performance signals observed for content can help identify content that is likely to show CTR improvement in a subsequent observation window. The analysis uses aggregated content-level search and engagement signals and compares a Week-4 rule-based baseline with Logistic Regression. A client-grouped train/test split was used so that clients in the training data did not appear in the test data, with zero client overlap. Logistic Regression achieved a ROC-AUC of 0.8153 and Average Precision of 0.3261, compared with 0.4814 and 0.1270 respectively for the Week-4 baseline on the same evaluation setup. The result is treated as observed predictive evidence and decision support rather than evidence of causality or proof of how a search engine ranking system works.

1. Introduction / Problem Statement

Search teams often need to decide which content deserves closer review. Reviewing every content item equally is inefficient, so a useful workflow needs a repeatable way to prioritize candidates.

The decision supported by this project is: which content items should receive higher priority for review based on observable search and engagement signals?

The project evaluates whether a simple machine-learning model can provide better ranking-oriented predictive information than the Week-4 rule-based baseline.

Important framing: The model identifies statistical patterns in the available data. It does not establish that any feature causes CTR improvement, and it does not prove anything about Google's ranking algorithm.

3. Methodology

Method choice

Logistic Regression was selected as the primary model because the task is binary classification and the model provides interpretable coefficients. Interpretability is useful for a decision-support workflow where the goal is not simply prediction, but also understanding which available signals are associated with the prediction.

Validation design

A grouped train/test split was used based on client identity. Each client was kept entirely within either the training set or the test set. This prevents the same client from appearing on both sides of evaluation.

Leakage check

The feature set was checked for label-derived columns. The final modeling features did not include the future CTR-improvement label itself. Future-window outcome information was not used as a predictive feature.

Evaluation metrics

ROC-AUC measures how well the model separates positive and negative observations across classification thresholds. Average Precision is also reported because the positive class represents only about 10% of the modeling population.

6. Error Analysis

On the evaluated test set, the confusion matrix was:

Predicted Negative Predicted Positive
Actual Negative 18,057 8,608
Actual Positive 566 3,326

The model produced 3,326 true positives and 566 false negatives, meaning most of the observed positive cases were captured at the selected classification threshold. However, it also produced 8,608 false positives. Therefore, the model is better suited to prioritization and review queues than to treating every positive prediction as a guaranteed outcome.

The strongest coefficient in absolute value was associated with GSC data availability, followed by the position-missing indicator and average position. This suggests that data availability and search-performance context are important parts of the model's decision boundary.

7. Limitations & Honest Framing

  • The results are measured on one grouped evaluation split and may not generalize unchanged to other data releases.
  • The target is an observed future-window outcome and does not establish causality.
  • Logistic Regression assumes a relatively simple relationship between features and the log-odds of the outcome.
  • The dataset is imbalanced, so accuracy alone would be misleading.
  • The model should be treated as a prioritization and decision-support system rather than an automated content decision maker.
  • The analysis does not demonstrate how Google's ranking system works and does not claim that any feature directly causes ranking or CTR changes.
Honest conclusion: The observed evaluation shows that Logistic Regression provided stronger predictive discrimination than the Week-4 baseline on the same grouped test setup. The evidence is directional and useful for prioritization, but further validation is needed before operational deployment.

8. Ranked Recommendations

1. Use the model as a review-prioritization queue

Rank content using model scores and send the highest-priority items for human review. Do not automatically change content based solely on the prediction.

2. Review high-score content with strong search visibility

Content receiving substantial impressions but showing a high predicted probability of improvement can be considered for closer CTR and metadata review.

3. Treat data availability as an explicit review factor

Because data-availability signals were important to the fitted model, analysts should distinguish genuine performance patterns from differences in measurement coverage.

4. Prioritize human investigation of false positives

The model produced 8,608 false positives on the evaluated threshold. Review these cases to identify situations where the model is systematically over-prioritizing content.

5. Revalidate before production use

Repeat evaluation on additional time periods or releases before treating the model as a stable operational ranking system.
